## The CX Sandbox

`{{cxsim: <lesson-id>}}` on its own line in a post body (or `{{cxsim}}` for the free sandbox) drops in a modelled AOS-CX terminal: `theme/cxsim/engine.js` is the switch (no DOM, so `node cxsimtest.js` drives it the way the widget does), `theme/widgets/cxsim.html` is the terminal, devices strip and task panel, and `theme/cxsim/lessons/<id>.json` is the lab. The build inlines the lesson JSON into the div and appends the engine and widget once per page, so it works offline like everything else and nothing is fetched. It is a model, not the box: output shapes follow the CX CLI reference but the wording is ours, `?` help and Tab completion come from the command table in the engine, and the footer says so on every embed. Addresses are RFC 5737 and MACs are `00:00:5e:00:53:xx`, so the publish grep never trips on it.

A lesson file carries `model` (`6200F-12` by default, also 24 and 48 port, a `6300M-48` and the Smart Rate `6300M-24SR5`; part numbers from HPE QuickSpecs), `hostname`, `startConfig` (CLI lines applied in config context at boot), `task` and `hints` (backticks become `<code>`), `devices` and `checks`. A device has a `kind` (`printer`, `laptop`, `phone`, `switch`, `router`, `loop`), a `port` or `ports`, a `mac`, optional `lldp`, and an `auth` block that says what the fake ClearPass answers per method (`{"mac-auth": {"accept": true, "role": "PRINTERS"}}`); a `switch` may carry `lacp`, `stpRoot` and `bpdu`, a `router` an `ip`, `vlan` and `ospf` block with the routes it advertises. `radius` names the server addresses that exist and the shared secret; anything else times out. Checks are declarative: `config` (a regexp under a running-config section), `client` (status, role, VLAN, method for a device), `vlan`, `lag`, `errdisabled`, `ospf`, `ping`, `route`, `hostname`, `saved`, `stp`. `sim connect|disconnect|coa|status|reset` are the sandbox talking, not the switch, and the Devices panel does the same with buttons. Progress lives in localStorage per page and lesson; Reset wipes it. Run `node cxsimtest.js` after touching the engine or a lesson: every lab's intended solution must pass its checks and the wrong turns must fail for the reason the lesson teaches. Downloadable user roles, VRFs beyond a name, and anything Central-managed are out of scope.

The fake ClearPass has a face (2026-10-05). Every request that reaches it becomes an Access Tracker row (`atRecord()`/`atEntry()` in the engine, `this.cppm.log`), shown in the ClearPass panel beside the terminal and by `sim cppm`: service, method, source, roles, enforcement profiles, error code and alerts in the wording ClearPass 6.11.1 gave on the bench (216 with the MSCHAP retry alert, 216 "User not found" for an unknown MAC, 9002 for a stalled supplicant; 206 for a policy deny is from the Policy Manager guide). A request that never arrives (wrong secret, unknown address) leaves no row, on purpose. Rows are added only when what ClearPass would see changes, so config edits that touch nothing do not flood it. An accepted row has Change Status with the four profiles ClearPass offers a vendor-Aruba NAD (`CPPM_COA`, `sim cppm change-status <row> <key>`): the two ArubaOS Wireless profiles NAK with Missing-Attribute, AOS-CX Disconnect is a Disconnect-ACK, AOS-CX Bounce the only CoA; counters are per dynamic-authorization client. Four more labs ride on it: `sc-11-timers` turns on the sandbox clock (`timers: true`, `sim wait <s>`; `dot1xWait()` holds a silent client 165 s or `initial-auth-response-timeout`, a stalled one `2 + 4 x eapol-timeout x max-eapol-requests` with 13.5 and 3 unset, which passes through the bench's 164, 122 and 42 s), `sc-12-coa`, `sc-13-tacacs` (a `tacacs` block with servers, key, users and editable profiles; `sim ssh <user>` logs the terminal in through the ssh login list; a header-only profile is Permission denied while Access Tracker says ACCEPT, `Aruba-Admin-Role` beats `priv-lvl`, command authorization locks out a user ClearPass does not know, the session's group sets the prompt and what runs) and `sc-14-ckauto` (`checkpoint auto`, the mgmt port, the reader's own SSH session that a mgmt change cuts, `sim console`). New check types: `waitmax`, `dyn`, `login`, `ckauto`, `mgmt`. A lab on sandbox.html counts a start only when the picker shows it (`root._cxsim.shown()`).

Anything the model does not carry is looked up in the real command set: `theme/cxsim/corpus/aoscx.js`, every template the AOS-CX Switch Simulator printed with `list` in sixteen contexts, one run each on 10.15.1060, 10.16.1060, 10.17.1030 and 10.18.1002, merged by `cxcorpus.py` into one shared trie per context whose edges carry the releases they exist in (about 2,800 nodes, 90 KB, loaded before the engine in the page and required under Node). A `{ a | b }` group in a template is a set the box takes in any order and combination (`ntp server X minpoll 4 maxpoll 4 iburst`, `radius-server host X key ... vrf mgmt`), so it is one edge into a shared little trie of its options (`s` in the corpus) that `walkReal` may re-enter, each option once, not an expansion of every ordering. The lab switch took `prefer iburst`, `iburst minpoll 5` and `vrf mgmt severity warning` and refused `iburst iburst` (2026-09-28); before sets, real multi-option lines were refused. A real command answers "This command is not used in this scenario." with a second line saying the switch has it; anything else gets the box's own error, `Invalid input: <first token it could not place>`, `% Command incomplete.` or `% Ambiguous command.`, and `?` merges the real words the model lacks. The raw `list` captures stay in the lab folder (10.18 in `~/Lab/aos-cx/audit-2026-09-28/corpus/`, the others in `~/Lab/aos-cx/harvest/<release>/`, harvested by `harvest/verlab.py`, `hv.txt` and `split.py` on throwaway VMs beside the lab) because the same logs carry the license banner; regenerate with the command in `cxcorpus.py`'s docstring.

Releases: the terminal head has an AOS-CX picker (and `sim release [<x>]` does the same from the keyboard). The syntax follows the picked release: a line the newest release takes but the picked one does not gets that release's own error plus a sandbox note saying when the syntax arrived (`releaseGate`), and unmodelled lines are looked up in that release's command set. Lines the sandbox feeds itself (a lesson's start config, a saved session, a rollback) are never gated. Output layouts are 10.18's except where the same config pushed to 10.15, 10.16 and 10.17 on 2026-09-28 showed a difference, which `atLeast()` applies: no `server ... priority` and no built-in `radius` group in 10.15's running-config, `Link state: up for N minutes (since ...)` in 10.15, the `Hardware port` line from 10.17, the LACP fallback legend and the OSPF `State:` legend only in 10.18. The simulator hides what needs a PHY (since 10.09 the CLI hides speeds the port cannot do, and it has no cable to test), so `theme/cxsim/corpus/hardware.txt` adds those back per context with the HPE guide each line came from: `speed` and `diag cable-diagnostic` so far. `OUTSIDE` is only the fallback when no corpus is loaded. Pipes follow 10.18: `include`, `exclude`, `begin` and `count` filter a show (regex, quoted when it has spaces, chained), `line-number` and `redirect` are real but not modelled, and `section`, `-i`, a bare pipe or a pipe after anything but show answer `Command not supported.` A 6200 model reports `ML.10.18.1002`, a 6300 `FL.10.18.1002`; a lesson can pin `version`.

Parity: on 2026-09-25 the same Lab 3 config was pushed to the real AOS-CX Switch Simulator 10.18.1002 (the QEMU lab in `~/Lab/aos-cx`, `cxlab.py`; captures in `~/Lab/aos-cx/parity/`, not committed because they carry the license banner and ciphertext secrets) and every `show` the engine imitates was diffed against it. Running-config block order, the built-in `radius` group with `priority`, the mgmt block, `show vlan`, `show interface brief`, the MAC table, LLDP, LACP, spanning tree, `show ip route` with its L routes, `show radius-server`, `show aaa server-groups`, the role listing, the empty-state wording (`No port-access clients found.`, `No OSPF neighbor found on VRF default.`, `No ARP entries found.`) and the three error strings (`Invalid input: <first unplaceable token>`, `% Command incomplete.`, `% Ambiguous command.`) now match the box. `Checkpoint list doesn't exist` is not an empty state: 10.18 has no `show checkpoint list` and reads `list` as a checkpoint name; the listing is `show checkpoint`. On 2026-09-26 and 2026-09-28 the NAC views were captured against ClearPass on the same bench (success by 802.1X and by MAC auth, server reject, server timeout, a role the switch lacks, multi-domain with a phone and a PC) and the engine now prints them in the box's layout: the flags table (`1x|c|-|s`, `--|c|-|f` for a failure), the detail blocks with Auth Precedence and Auth History, `show aaa authentication port-access interface all client-status`, `show radius-server statistics authentication` and `show radius dyn-authorization`. Behaviour the lab taught and the engine now follows: a new LAG is created shut down until `no shutdown`; CoA needs `radius dyn-authorization client <ip> secret-key ...` as well as `enable`, and without it the request is dropped and counted as an invalid client address; `clear port-access clients`, `show aaa authentication port-access` and `show radius-server statistics` do not exist or are incomplete on 10.18 (the real ways are `port-access log-off client ...`, `port-access reauthenticate interface ...` and `show radius-server statistics authentication`). The fallback role wording (`<role>, Critical`) follows HPE's documentation; the lab never produced one. Re-run the diff after any engine change to a `show`: push `parity/lab3.txt` with `cxpush.sh`, capture with `parity/capture.exp`, compare by eye.

`sandbox.html` is the page: every lab from `SANDBOX_LABS` in `build-blog.py` behind a picker (`#lab=<id>` deep links), the engine inlined once, an OG card and a sitemap entry, and a band on `academy.html` pointing at it. Since 2026-09-30 all five CX pages sit under the Tools nav pill (`active="tools"`), and `tools.html` carries a CX strip (`#cx`) linking them above the planners. Everything runs in the reader's browser, so any number of people can use it at once and the site never runs anything for them. Four pages sit around it, tied together by the `cx_tools()` strip of outline pills (the orange ring stays the nav's) and one search box beside it: `cx_index()` builds a small JSON index at build time (commands, labs, practices, CIS controls, releases, diagrams), inlined on every CX page because the checker and builder allow no requests, and `CX_UI_JS` jumps to the page and opens the row (`#n-<slug>`, `#lab=<id>`, `#p-<slug>`, `#cis-<id>`, `#r-<rel>`, `#fig-cx-<name>`); `/` focuses it. Long lists are compact rows (`cx_row()`, a `<details class="cxr">`, so they read without JavaScript) with Expand all; the lab picker is one collapsible, filterable list with Previous and Next, and its buttons keep `.sb-pill[data-lab]` for the progress ticks. `cx-notes.html`, `cx-check.html`, `cx-build.html` and `cx-guide.html`, each with an OG card and a sitemap entry.

Command notes: `theme/cxsim/notes.json` is the source, one note per command (`k` the command with `<placeholders>` and `<a|b>` alternations, `c` context, `g` group, `t`, `w`, two or three `ex` examples, `v` release callouts, `fake` where the sandbox pretends, `tip`, `see`, `fig`, `m` a model for the examples, and `rel`, the releases whose command set takes it). `node cxnotes.js` runs every example through the engine and checks every `rel` against the corpus; `--write` recomputes `rel` after the corpus changes. The widget's About this command band finds the note for the line being typed or clicked through `sim.note()` (the engine's `canon()` spells the line the way the command table does, in the current context, and an ambiguous abbreviation stays unmatched), and an example button types its lines in one at a time. `cx-notes.html` is every note by group with the four diagrams (`graphics/fig-cx-radius.svg`, `-lldp-med`, `-lacp`, `-mda`) and the habits under each (`CX_FIGS` in `build-blog.py`).

The config checker (`cx-check.html`, `theme/cxsim/checker.js`): paste a running config, and every line is asked of the picked release's command set in the context its indentation puts it in (`CXSim.syntax(ctx, line, release)`), every name it uses is checked against what it defines (VLANs, roles, RADIUS groups and servers, LLDP groups, LAGs, UBT zones, OSPF processes, VSF member ports), and the rest is held to the CIS benchmark by control number and to the practices. It never makes a request, and the page carries a CSP with `connect-src 'none'` (`CX_CSP`), so the promise on the page is enforced by the browser. The sample is `theme/cxsim/samples/check-sample.cfg`. Lines in contexts the corpus does not cover (`interface mgmt`, `password complexity`, `cli-session`, a banner's text) are counted, not judged.

The script builder (`cx-build.html`, `theme/cxsim/builder.js`): answers in, a paste-ready config out, block by block with why and the show commands that prove it. `verify()` holds every build to the release's command set and pastes it into a fresh engine of the chosen model; `cxsimtest.js` does that for every model, release and six feature mixes. It hands off through this browser's storage only: `cxsim:import` to the free-play lab (`sandbox.html#lab=sandbox&import=1`, which pastes it with the shared secret swapped for the bench's) and `cxcheck:import` to the checker (`cx-check.html#import`); each side deletes the key as it reads it. Same CSP as the checker.

Releases and hardening (`cx-guide.html`): the Feature Navigator's rows for the 6200 and 6300 (`theme/cxsim/features.json`, read from `feature-navigator.arubanetworking.hpe.com/api/switchReleaseCompatibility` on 2026-09-28; 10.18 is not in it yet), the command-line difference between each release's lists computed from the corpus at build time (`cx_corpus_forms()`), the notes' callouts per release, `theme/cxsim/practices.json`, and `theme/cxsim/cis.json`: the 28 controls of the CIS HPE Aruba Networking CX Switch Benchmark v1.0.1 L1 by control number (from the public Tenable audit file; the wording is ours, the CIS text is not reproduced). `cxsimtest.js` checks every config line on the page against the command set, and that every control the checker can raise is on it.

Usage events: the same Worker as comments takes `POST /v1/sandbox/events` (table `sandbox_events`, `comments/schema-sandbox.sql`); `SANDBOX_API` at the top of `build-blog.py` is what the embeds post to, empty to send nothing. The widget sends a random per-browser id, the lesson, and only these: start, a rejected command with its error kind (never a command that worked), Check my work with the pass count, done, reset, hint, device connects, and any JavaScript error. The footer tells the reader. `python3 cxstats.py` turns that into users, attempts per user, pass rate and the commands that fail most per lab; `--errors` lists the JS errors. One-time: `wrangler d1 execute nfn-comments --remote --file=schema-sandbox.sql` then `wrangler deploy` from `comments/`; until the Worker is redeployed the events 404 and nothing else notices.
